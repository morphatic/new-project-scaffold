# Conversation I had with Claude on Implementing New Project Automation

<prompt>
I use Claude Code a lot for software projects. I'm developing a "new project workflow" that will automate all of the steps of setting up new projects on my system. This is designed to be triggered from an empty folder on my machine and will handle things like setting up a minimal folder structure, setting permissions, installing tooling and config files, and getting me started on preparing the planning documents that will end up steering the actual design and implementation of the project. What is the best set of primitives for me to use to implement this, i.e. tools, hooks, local/project/global config files, skills, MCP, etc? Given that this workflow is only something that needs to be triggered once per project, and I won't be starting new projects except maybe a few times a year, it shouldn't be something that will continually need to be loaded into context or consume tokens on an ongoing basis.
</prompt>

Great use case. Here's how I'd think about the primitives:

## Recommended Approach: Shell Script + Claude Code Global Custom Instructions (Minimal)

Since this is a one-shot trigger that shouldn't pollute ongoing context, the right architecture keeps most logic *outside* Claude Code and uses CC only where its strengths shine.

---

## The Core Primitives

### 1. A Shell Script as the Entry Point (Primary Workhorse)

A script (e.g., `new-project`) that you invoke from your empty folder handles all the deterministic, mechanical work:

- Scaffold folder structure
- Copy/symlink config files (`.editorconfig`, linting, gitignore, etc.)
- Run `git init`, set permissions, install base tooling
- Generate a CLAUDE.md stub

This should do *everything* that doesn't require intelligence. Don't make Claude Code do file I/O that a shell script can do reliably and repeatably.

### 2. CLAUDE.md (Project-Level) — Generated by the Script

Your script generates a minimal `CLAUDE.md` in the new project root. This is the bridge to Claude Code. It should contain:

- The project name and type (captured from prompts during the script)
- A pointer to the planning docs it needs to help you complete
- Any project-specific conventions Claude should know

This file is only loaded when you open CC in that project, so it has zero ongoing cost elsewhere.

### 3. A "Planning Prompt" Template File

Keep a versioned `planning-prompt.md` template somewhere central (e.g., `~/.config/new-project/templates/`). Your script copies this into the project. It's a structured prompt you run *once* in Claude Code to generate your planning documents (architecture, requirements, decisions log, etc.).

This separates the "what to ask" from the "how to set up," and you can evolve it independently.

### 4. Global `CLAUDE.md` — Keep It Minimal / Don't Use It For This

Your global `~/.claude/CLAUDE.md` is loaded into *every* CC session. Do **not** put new-project workflow logic there — it would burn tokens on every unrelated project. Reserve it for truly universal preferences (coding style, communication preferences, etc.).

### 5. Claude Code Slash Commands (Optional, Lightweight)

If you want a CC-native trigger, you can create a project-level slash command at `.claude/commands/init-planning.md`. This would contain the planning prompt template and be invoked with `/project:init-planning` after the shell script has run. This is a clean, explicit, one-time trigger with no passive context cost.

---

## What I'd Skip (For This Use Case)

- **MCP**: Overkill for a once-per-project script. Only worth it if you're integrating with external services (Jira, Notion, etc.) that don't have CLI access.
- **Hooks**: Hooks fire on CC lifecycle events (tool use, responses, etc.) — they're for ongoing behavioral guardrails, not project initialization.
- **`settings.json` customization**: Useful for per-project tool permissions, but not necessary for a setup workflow.

---

## Suggested Flow

```text
cd ~/projects/my-new-thing
new-project          # Your shell script runs
                     #   → scaffolds folders
                     #   → installs tooling
                     #   → generates CLAUDE.md + planning-prompt.md
                     #   → creates .claude/commands/init-planning.md

claude               # Open Claude Code in the project
/project:init-planning  # One-shot: generates your planning docs
```

After that, the setup artifacts are inert files. No ongoing token cost, no polluted global context.

---

## Summary Table

| Primitive | Use It? | Why |
| --------- | ------- | --- |
| Shell script | ✅ Yes | Deterministic setup, zero AI cost |
| Project `CLAUDE.md` | ✅ Yes | Context for CC, generated once |
| `/project:` slash command | ✅ Yes | Clean one-shot planning trigger |
| Planning prompt template | ✅ Yes | Versioned, reusable, separates concerns |
| Global `CLAUDE.md` | ⚠️ Sparingly | Only for universal prefs |
| MCP | ❌ Skip | Overkill for local-only workflow |
| Hooks | ❌ Skip | Wrong lifecycle for this use case |
